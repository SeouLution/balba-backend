## 출처 간 우선순위

1. 공개 HTTP 계약은 `openapi.yaml`이 최우선이다.
2. 저장 구조는 `docs/erd.dbml`을 따른다. 이 스펙은 ERD에 없는 테이블·컬럼을 쓰지 않는다. 더 필요해지면 ERD를 먼저 고친다.
3. 데이터의 출처와 의존 흐름은 PDF를 따른다.
4. Figma는 사용자 흐름을 확인하는 용도다. Figma 화면의 예시 숫자는 서로 맞지 않는 곳이 있으므로 계산 기준으로 쓰지 않는다.

PDF의 흐름은 `POS 판매 → 요일 평균 → 날씨/행사 보정 → 준비량 → 레시피별 재료 필요량 → 재고 차감 → 구매 단위 발주`다. `영수증 → 거래처/단가/입고`, `입고 − 사용 → 남은 재고`, `재고+유통기한 → 할인 후보`, `POS 금액÷수량 → 판매가 → 할인 절감`이 연결된다. 푸시는 20:00/07:30, 할인 판단 기준은 17:00이다. 이 중 `재고+유통기한 → 할인 후보`는 따르지 않는다(D04, D37).

| U02 | 새 POS 파일의 기간이 이미 반영된 파일과 겹치고 기존 판매 칸이 새 파일에 없음 | 전체 매출 정정본이면 0, 일부 메뉴만 추출한 파일이면 기존 판매가 될 수 있다. 지원 범위와 교체 단위는 미정이다. 온보딩 시연은 첫 업로드와 같은 import의 확정 재시도로 검증한다. 결정 전까지는 새 파일에 행이 있는 칸만 교체하고, 새 파일에 없는 기존 칸은 건드리지 않는다. |
| U03 | 서울 문화행사 자료에는 시작·끝 시각이 없고 날짜만 있음 | EVENT_TODAY 제목 `오늘 근처 행사 · {시작} ~ {끝}`이 `00:00 ~ 00:00`으로 나오고, 붐비는 시간 문구의 `{행사 시작 H}시`가 0시가 된다(2026-11-20 실제 자료로 확인). 시각 대신 행사 이름이나 기간을 쓸지 미정이다. 결정 전까지 현재 템플릿을 유지한다. 행사 목록(`EventSummary.startAt/endAt`)은 00:00~다음 날 00:00으로 내려가며 표시 방식은 프론트가 정한다. |

U01~U03에만 의존하는 처리와 인수 기준은 결정 후 추가한다. 구현자가 임의로 우선순위나 오류 응답을 정하지 않는다.

## 현재 공개 계약이 표현하지 못하는 것

스펙은 아래 항목을 위해 필드나 엔드포인트를 몰래 늘리지 않는다. 필요하면 `openapi.yaml`을 먼저 고친다.

- 재료 탭의 남은 일수("9일 남았어요")와 "단위 추정" 표시는 `IngredientSummary`에 필드가 없다.
- 거래처별 발주 마감 시각("마감 21:00")은 `Supplier`·`OrderPlanSupplier`에 필드가 없다.
- 영수증 공개 줄에는 품명·단가·전화번호·환산 비율이 없다. 내부 결과에만 보관한다.
- 읽지 못한 영수증을 알리는 전용 필드가 없다(D23).
- 단가 없음, 주문 요일 모름, AI 실패를 알리는 필드가 없다.
- 작업 실패 상태(FAILED)와 다시 시도하는 API가 없다(D07).
- 영수증 정정, 재고 실사, 단위 수정 화면이 없다.
- 같은 날 안에서 입고와 사용의 시각 순서를 알 수 없다. 하루 시작에 입고, 하루 끝에 사용 차감으로 계산한다.

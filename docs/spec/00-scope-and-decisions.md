## 출처 간 우선순위

1. 공개 HTTP 계약은 `openapi.yaml`이 최우선이다.
2. 저장 구조는 `docs/erd.dbml`을 따른다. 이 스펙은 ERD에 없는 테이블·컬럼을 쓰지 않는다. 더 필요해지면 ERD를 먼저 고친다.
3. 데이터의 출처와 의존 흐름은 PDF를 따른다.
4. Figma는 사용자 흐름을 확인하는 용도다. Figma 화면의 예시 숫자는 서로 맞지 않는 곳이 있으므로 계산 기준으로 쓰지 않는다.

PDF의 흐름은 `POS 판매 → 요일 평균 → 날씨/행사 보정 → 준비량 → 레시피별 재료 필요량 → 재고 차감 → 구매 단위 발주`다. `영수증 → 거래처/단가/입고`, `입고 − 사용 → 남은 재고`, `재고+유통기한 → 할인 후보`, `POS 금액÷수량 → 판매가 → 할인 절감`이 연결된다. 푸시는 20:00/07:30, 할인 판단 기준은 17:00이다. 이 중 할인으로 이어지는 흐름 전체(`재고+유통기한 → 할인 후보`, `판매가 → 할인 절감`, 17:00 판단)는 따르지 않는다(D04, D42). `요일 평균 → 날씨/행사 보정`은 D39의 예측 모델로, `입고 − 사용`의 사용은 D03의 POS 판매량으로 바뀌었다. `구매 단위 발주`는 재료 단위(개·g) 발주로 바뀌었다(D47).

## 현재 공개 계약이 표현하지 못하는 것

스펙은 아래 항목을 위해 필드나 엔드포인트를 몰래 늘리지 않는다. 필요하면 `openapi.yaml`을 먼저 고친다.

- 재료 탭의 남은 일수("9일 남았어요")는 `IngredientSummary`에 필드가 없다.
- 영수증 줄의 입고량이 포장량을 읽은 값인지 추정한 값인지 알리는 필드가 없다(D50).
- 재고 부족은 홈 배너의 문장으로만 전달한다. 재료별 부족 여부·남은 양·이미 발주했는지를 담는 필드는 없다. 배너를 눌렀을 때 여는 화면은 프론트가 배너 type으로 정한다.
- 재고가 어느 날짜의 판매 기록까지 반영된 값인지 알리는 필드가 없다(D03).
- 예측 모델의 가중치와 오차를 보여주는 필드가 없다(D40).
- 거래처별 발주 마감 시각("마감 21:00")은 `Supplier`·`OrderPlanSupplier`에 필드가 없다.
- 영수증 공개 줄에는 품명·단가·전화번호가 없다. 내부 결과에만 보관한다.
- 읽지 못한 영수증을 알리는 전용 필드가 없다(D23).
- 단가 없음, 주문 요일 모름, AI 실패를 알리는 필드가 없다.
- 작업 실패 상태(FAILED)와 다시 시도하는 API가 없다(D07).
- 영수증 정정, 재고 실사, 단위 수정 화면이 없다.
- 같은 날 안에서 입고와 사용의 시각 순서를 알 수 없다. 하루 시작에 입고, 하루 끝에 사용 차감으로 계산한다.

## 검토가 필요한 정책 값

`[upload] sales_max_rows = 100000`, `sales_file_max_mib = 20`. 한도는 엑셀 원본 줄 수에 걸린다. 날짜·메뉴별 합계 형식이면 2년치도 들어가지만, 주문 건별 형식은 하루 300줄만 팔려도 2년치가 약 19만 줄이라 거절된다. POS 내보내기 형식을 확인한 뒤 정한다.

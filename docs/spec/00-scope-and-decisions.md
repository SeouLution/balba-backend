## 출처 간 우선순위

1. 공개 HTTP 계약은 `openapi.yaml`이 최우선이다.
2. 저장 구조는 `docs/erd.dbml`을 따른다. 이 스펙은 ERD에 없는 테이블·컬럼을 쓰지 않는다. 더 필요해지면 ERD를 먼저 고친다.
3. 데이터의 출처와 의존 흐름은 PDF를 따른다.
4. Figma는 사용자 흐름을 확인하는 용도다. Figma 화면의 예시 숫자는 서로 맞지 않는 곳이 있으므로 계산 기준으로 쓰지 않는다.

PDF의 흐름은 `POS 판매 → 요일 평균 → 날씨/행사 보정 → 준비량 → 레시피별 재료 필요량 → 재고 차감 → 구매 단위 발주`다. `영수증 → 거래처/단가/입고`, `입고 − 사용 → 남은 재고`, `재고+유통기한 → 할인 후보`, `POS 금액÷수량 → 판매가 → 할인 절감`이 연결된다. 푸시는 20:00/07:30, 할인 판단 기준은 17:00이다.

## 현재 공개 계약이 표현하지 못하는 것

스펙은 아래 항목을 위해 필드나 엔드포인트를 몰래 늘리지 않는다. 필요하면 `openapi.yaml`을 먼저 고친다.

- 재료 탭의 남은 일수("9일 남았어요")와 "단위 추정" 표시는 `IngredientSummary`에 필드가 없다.
- 거래처별 발주 마감 시각("마감 21:00")은 `Supplier`·`OrderPlanSupplier`에 필드가 없다.
- 영수증 공개 줄에는 품명·단가·전화번호·환산 비율이 없다. 내부 결과에만 보관한다.
- 읽지 못한 영수증을 알리는 전용 필드가 없다(D23).
- 단가 없음, 주문 요일 모름, AI 실패를 알리는 Alert 종류가 없다. `PRICE_CHANGED`로 대신하지 않는다.
- 작업 실패 상태(FAILED)와 다시 시도하는 API가 없다(D07).
- 영수증 정정, 재고 실사, 단위 수정 화면이 없다.
- 같은 날 안에서 입고와 사용의 시각 순서를 알 수 없다. 하루 시작에 입고, 하루 끝에 사용 차감으로 계산한다.

# 검증 기준과 인수 시나리오

아래는 구현 작업의 완료 조건이다. 각 엔드포인트 문서의 완료 조건을 함께 실행한다.

## 검증 계층

| 계층 | 대상 | 방법 |
|---|---|---|
| 계약 | 가게 API 20개 method/path/operationId, 요청·응답 모양 | `openapi.yaml`을 직접 읽어 라우트와 대조하고, 실제 HTTP 응답을 그 스키마(JSON Schema 2020-12)로 검증 |
| 단위 | 예측·예측 모델·재고·발주·재고 부족 계산, 문장 템플릿 | 고정 Clock, Decimal, 정책 값 fixture. 외부 IO 없음 |
| 통합 | PostgreSQL 제약/잠금/트랜잭션/작업 | 실제 PostgreSQL + 임시 파일 저장소 + fake 외부 포트 |
| 인수 | 온보딩 → 홈 → 발주 → 영수증 → 재고 부족 안내 | FastAPI client와 실제 작업 handler, 고정 Clock |
| 복구 | 재시작/재시도/DEAD | commit 전후 중단, 같은 작업 두 번 실행 |
| 공급자 매핑 | 외부 응답 → 내부 타입 | `tests/fixtures/providers/`에 저장한 실제 응답으로 검증. 기본 테스트는 실제 API를 부르지 않음 |
| 운영 회귀 | 기존 배포 계약 | `/health` GIT_SHA, `/openapi.yaml` 원본 byte 일치, `/scalar`, ARM64 이미지 |

if/then 조건, Decimal의 JSON number, nullable과 필드 생략, 204 빈 body는 실제 응답으로 검증한다.

## 공통 계약 매트릭스

20개 operation 각각에 대해 정상 상태 코드와 body, 없는 store, 다른 store의 하위 ID, 구조 오류, 예상하지 못한 adapter 실패를 확인한다.

- 모든 오류 body가 `{code}` 한 키뿐이다. FastAPI detail, stack, 외부 서비스 문구가 없다.
- 수량에 bool/NaN/Infinity/음수는 422. 소수 6자리 초과는 6자리로 반올림돼 저장된다(D26).
- 모르는 값: 선택 non-nullable 필드는 생략, 필수 nullable 필드는 null로 존재.
- body 없는 confirmSalesImport 202와 모든 204는 bytes 길이 0.
- 다른 store의 menu/supplier/ingredient/import/scan/order ID는 조회와 batch 양쪽에서 404.
- 빈 목록, 0, null을 서로 바꾸지 않는다.
- batch의 한 항목이 오류면 DB 전체가 그대로다.

## 계산 기준 fixture

### F01 예측

**추천 준비량**: 대상일 2026-11-14(토). 모델은 `weights={weekday:1, weather:1}`, `weekdayIndex` 토요일 1.2·그 외 1.0. 이전 28일 학습일은 토요일 4일(각 60인분)과 그 외 20일(각 50인분)이다. 판매합 1,240 ÷ 요일 계수합 24.8 → level=50, baseline=60.

- 날씨·행사 계수 1.0이면 recommended=60, eventDiff=0, diff=0, SIMILAR, summaryText `평소 토요일 60인분`.
- 행사 계수 1.2면 recommended=72, eventDiff=12, diff=12, MORE, summaryText `평소 토요일 60인분 · 행사 +20%`.
- 대상일 날씨 구간의 `weatherIndex`가 0.8이면 recommended=48. `weights.weather=0.5`면 계수 0.9로 54다.
- 대상일 날씨 구간에 값이 없으면 예보가 RAIN이어도 보정하지 않아 60이다. 날씨를 모를 때도 60이다.
- `weights.weekday=0.5`면 토요일 계수 1.1, 요일 계수합 24.4, level≈50.82, baseline≈55.90, recommended=56이다.
- 모델이 없으면 요일 계수는 전부 1.0이다. level=baseline=1,240÷24≈51.67, recommended=52다.

이전 28일에 학습일이 하나도 없으면 그 메뉴의 예측을 만들지 않는다. 첫 판매 파일 기간 안에서 행이 없는 날은 0으로 학습일에 들어간다. 다른 파일과 기간이 겹칠 때 누락 칸의 기대값은 미정(U02)이다. `adjusted=0`이면 planned=0이고 예측을 다시 만들어도 0이다.

**요일 경향**: 월~토 영업, 학습일 12일(2주). 가게 전체 판매가 평일 100, 토요일 160이면 전체 평균 110, 토요일 `weekdayIndex`≈1.4545, 평일≈0.9091이다. 학습일이 없는 일요일은 1.0이다. 학습일이 1일뿐인 요일도 1.0이다.

**날씨 경향**: 메뉴 평균 50, 요일 경향 전부 1.0. `(10℃ 이상 20℃ 미만, 강수)` 구간의 학습일 5일 판매합이 200이면 `weatherIndex`=200÷250=0.8이다. 그 구간의 학습일이 4일이면 값을 만들지 않는다. 계산값이 0.3이면 0.5로 자른다. 관측 행이 없는 학습일은 어느 구간에도 들어가지 않는다. 일 강수량 0.9mm는 강수가 아니고 1.0mm는 강수다. 최고기온 20.0℃는 `20℃ 이상 28℃ 미만` 구간이다.

**가중치 조절**: 학습일 55일이면 조절하지 않고 두 가중치를 1.0으로 저장하며 `holdoutError`는 null이다. 56일이면 앞 28일로 경향을 구하고 뒤 28일로 25개 조합의 오차를 구해 가장 작은 조합을 저장한다. 저장하는 `weekdayIndex`·`weatherIndex`는 56일 전체로 다시 계산한 값이다. 요일에 따라 판매가 뚜렷이 다른 자료에서는 `weights.weekday=0`인 조합이 뽑히지 않는다. 날씨와 판매가 무관한 자료에서 오차가 같은 조합이 여럿이면 weekday가 큰 조합, 그다음 weather가 큰 조합이 뽑힌다. 같은 자료로 두 번 계산하면 `fittedAt`을 뺀 모델이 같다.

밤사이 변경: 밤 추천 50 → 아침 다시 만들어 48이면 previousRecommended=50. 아침에 한 번 더 만들어 48이면 그대로 50. MORNING 입력이 밤과 같은 경우와 NIGHT 기록이 없는 경우는 null이다. 이후 낮 DATA_CHANGED가 46으로 바꾸면 밤사이 변경을 새로 표시하지 않는다.

### F02 재고·발주

김밥 1인분당 계란 1개.

- 11/8 영수증 '특란 30구 2판'을 확정해 계란 60개 입고. 11/8~11/9는 판매 기록이 있고 김밥이 20인분, 25인분 팔림 → 11/9 끝 재고 15개.
- 11/10은 판매 기록이 없다. 예측 행의 planned=10, produced=12가 있어도 11/10 끝 재고는 15개 그대로다(D03).
- 11/10 판매 10인분이 든 엑셀을 반영하면 11/10 끝 재고는 5개가 된다.
- 입고 기록이 없는 재료는 stock=null이다.
- 사용량이 재고보다 많은 날은 재고 0으로 두고 다음 날로 넘어간다.

발주: 재고 15개, 계획 75인분 → 부족 60개 → 발주 60개. 행사 없는 준비량 60인분이면 부족 45개이므로 eventDiff=15개. 30개를 8,900원에 산 영수증의 단가는 296.666667원이고 60개의 줄 금액은 17,800원이다. 떡 재고 1,500g, 필요 6,037.5g이면 발주 4,538g이다. 입고 기록이 없는 재료는 거래처를 몰라 발주 줄에 없다.

금액: 줄 3개 중 단가를 아는 줄이 2개면 합계는 그 2개의 합이다. 하나도 모르면 null. 줄이 없으면 `suppliers=[]`, `Home.order=null`.

단위 환산(D47): 영수증 '특란 30구' 2판은 60개, '떡볶이떡 2kg' 3봉은 6000g, '진간장 1.8L' 2통은 3600g으로 입고된다. 포장량이 없는 '계란 1판'은 AI가 추정한 양으로 입고된다(D50). 단위가 개인 계란에 g으로 읽힌 줄은 빠지고 '못 읽은 줄' 안내가 온다(D31). 레시피 초안이 `장`이나 `ml`로 답한 항목은 버린다. 모든 메뉴의 `unit`은 `인분`이고 이름이 '참치김밥'이어도 같다(D46).

발주서 생성, 전송 기록, 준비량 PUT, 만든 양 PUT으로는 재고가 바뀌지 않는다. 재고를 바꾸는 것은 영수증 확정과 판매 반영뿐이다.

### F04 행사 분류

같은 날 같은 시간대의 행사 5건(축제-문화/예술, 콘서트, 교육/체험, 전시/미술, 분류 없음)을 받으면 축제와 콘서트 2건만 저장한다(D29). 반경 안에 교육/체험 행사만 있으면 행사 계수는 1.0이고 홈 행사 목록은 비어 있다.

### F03 재고 부족 안내

김밥 1인분당 계란 1개. `policy.low_stock.days=2`.

- targetDate와 다음 날 준비량이 60인분씩이면 expectedUsage=120개다. 재고 100개면 부족이고 120개면 부족이 아니다.
- 다음 날의 예측 행이 없으면 날씨·행사 계수를 1로 둔 예측값을 올림해 쓴다. 그날 일부 메뉴의 예측 행만 있으면 없는 메뉴만 그렇게 계산한다. 다음 날이 휴무면 그다음 영업일을 쓴다.
- 사장님이 targetDate 준비량을 40인분으로 고치면 expectedUsage는 100개가 되고 재고 100개는 부족이 아니다.
- `stock=null`인 재료, 레시피에 쓰이지 않는 재료는 목록에 없다.
- 계란의 최근 입고일이 11/8이고 계란이 든 발주서를 11/9에 보냈으면 `ordered=true`다. 발주서를 만들기만 하고 보내지 않았거나, 11/10 날짜 영수증을 확정한 뒤에는 `ordered=false`다.
- 배너: 부족 재료가 계란(ordered=false)뿐이면 title `계란 재고가 얼마 안 남았어요`, message `발주해 주세요 · 이미 발주했다면 영수증을 올려주세요`. 계란·김·떡 3개면 title `계란·김 외 1개 재고가 얼마 안 남았어요`. 전부 ordered=true면 message `이미 발주한 재료예요 · 받았다면 영수증을 올려주세요`.
- NIGHT 푸시 body: 발주하지 않은 부족 재료가 계란·김이면 `김밥 60인분 등 12개 메뉴 · 계란 외 1개 발주가 필요해요`. 부족 재료가 전부 ordered=true거나 없으면 발주 문구가 없다. MORNING 푸시에는 붙지 않는다.

## 인수 흐름

### A01 온보딩

1. 가게 생성 201 → 푸시 구독 등록 204.
2. 판매 업로드 202 → PARSE_SALES(열 판별 fake) → NEEDS_CONFIRMATION의 columnMapping/preview 확인.
3. confirm 202 → APPLY_SALES → COMPLETED → FIT_FORECAST_MODEL → 오늘·내일 예측. confirm을 반복해도 판매합이 같다. 과거 날씨 호출이 실패해도 `store.forecast_model`이 저장되고 예측이 만들어진다.
4. GENERATE_RECIPES 완료 → recipes GET의 `generationStatus`가 READY.
5. 영수증을 건너뛰고 recipes GET(모든 재료 항목) / PUT.
6. NIGHT 예측 완료 후 20:00 이후 홈 200: 예측 있음, FIRST_FORECAST 배너, `order=null`(거래처 없음).

### A02 영수증과 발주

1. JPEG 여러 장 접수 202, PROCESSING → NEEDS_REVIEW. receipt_line은 아직 0건.
2. 같은 영수증을 두 번 넣은 경우 한 장만 남고 안내가 온다. 읽지 못한 사진은 빠지고 안내가 온다.
3. 질문에 SAME/DIFFERENT로 답하고 confirm 204 → 거래처·재료·입고가 한 번에 생긴다.
4. 같은 사진의 A·B 스캔을 모두 NEEDS_REVIEW로 만든 뒤 A, B를 확정한다. 둘 다 204, 같은 사진의 입고는 한 번이다. B를 조회하면 중복 안내가 있다. 같은 날 다른 품목 사진은 반영되며, 이후 A 사진만 다시 올려도 입고는 늘지 않는다.
5. 같은 품명이 다음 scan에 다시 나오면 질문 없이 같은 재료에 연결된다.
6. 주문 요일 확정 204 → getOrderPlan에 오늘 주문 요일인 거래처만 나온다. 줄마다 stock이 숫자로 나온다.
7. 20시 이후 내일 준비량을 변경한다. 200의 item·order는 같은 UoW의 변경값을 반영하고, 뒤이은 홈·발주 상세와 수량·금액이 일치한다.
8. 발주서 생성 201 → send-records 204. 재고는 그대로이고 생성 당시 금액이 고정된다.

### A03 당일 아침과 재고 부족 안내

1. 자정이 지나면 홈이 TODAY, targetDate 오늘. 어젯밤 보낸 발주서가 있으면 DELIVERY_EXPECTED에 품목이 나열된다.
2. produced PUT 204 → 홈에 반영되고 daily_sales와 재고는 그대로다.
3. 판매 엑셀을 반영해 재료의 재고가 2영업일 예상 사용량 아래로 내려가면 홈에 LOW_STOCK 배너가 나온다. 조회 전후로 DB 행 수가 같다.
4. 그 재료가 든 발주서를 만들어 send-records까지 기록하면 배너 message가 영수증 안내로 바뀐다(부족 재료가 그것뿐일 때).
5. 그 재료의 영수증을 확정해 재고가 예상 사용량 이상이 되면 배너가 사라진다.

### A04 실패와 복구

202 직후 서버 재시작, 외부 호출 timeout, 파일 없음, AI의 스키마 위반, 전부 읽지 못한 영수증, 같은 가게 동시 PUT을 각각 재현한다. 상태가 끝없이 진행 중으로 남지 않고 성공 또는 DEAD(조회 500)로 끝나며, 업무 데이터가 두 번 반영되거나 일부만 남지 않는다. 열을 찾지 못한 엑셀은 DEAD가 아니라 NEEDS_CONFIRMATION(찾지 못한 열 null, recordCount 0)으로 끝나고, confirm은 422, 열 바꾸기 뒤에는 정상 반영된다.

### A05 화면 간 일치

| 시작 상태와 행동 | 기대 결과 |
|---|---|
| 20시 이후 부족 재료가 있는 가게의 홈 조회와 같은 대상일의 NIGHT 푸시 발송 | 홈 LOW_STOCK 배너의 재료와 푸시 발주 문구의 재료가 같은 `FindLowStock` 결과에서 나온다. 푸시에는 `ordered=false`인 재료만 들어간다. |
| 20시 이후 부족 재료가 있는 상태에서 getOrderPlan 조회 | 발주 계획의 stock과 부족 판단에 쓴 재고가 같은 값이다(둘 다 오늘 영업 종료 기준). |
| 20시 전 부족 배너가 뜬 상태에서 오늘 날짜 영수증을 확정 | 재고가 예상 사용량 이상이 되면 다음 홈 조회에서 배너가 사라진다. |
| 전날 밤 행사에 장소와 혼잡도 정보가 없고 그 행사가 발주 계수에 반영됨 | 홈·발주 상세 모두 200. 양쪽 EventSummary에서 place·crowdLevel 키가 생략된다. |
| 같은 대상일의 NIGHT 추천 50, MORNING 작업 지연, 07:30 푸시 작업 실행 | 밤 수량을 보내지 않고 대기한다. 대기 기한 안에 아침 추천 48로 성공하면 푸시 문구는 48, 홈의 previousRecommended는 50이다. |
| 같은 import를 여러 번 확정 | 판매와 최초 후속 작업은 한 번만 반영된다. |

기간이 겹치는 별도 POS 파일의 누락 판매, 시각이 없는 행사의 배너 문구는 [미정 정책 U02~U03](00-scope-and-decisions.md)으로 추적한다. 정책 확정 전에는 기대값을 두지 않는다.

## 구현 완료 체크

- 20개 엔드포인트 문서의 완료 조건을 operationId별 테스트에 연결했다.
- Alembic migration이 빈 DB에 적용된다. 테이블·컬럼이 `erd.dbml`과 일치한다.
- 외부 포트마다 fake와 실제 adapter가 같은 계약을 만족한다. 실제 adapter는 저장한 실제 응답 fixture로 검증했다.
- 모듈 경계를 ORM 객체나 임의 dict로 넘기지 않는다.
- `openapi-spec-validator openapi.yaml`, `ruff check .`, `pytest -q`를 통과한다.
- OpenAPI/ERD와 다르게 구현한 부분이 없다. 생겼다면 테스트로 가리지 않고 결정 원장에 적는다.
